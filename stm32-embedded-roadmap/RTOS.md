# FreeRTOS 入职基础

不要因为会创建两个任务就认为掌握 RTOS。核心是理解状态、通信、同步和资源预算。

## 任务状态

```text
Running：正在 CPU 上执行
Ready：可以运行，等待调度
Blocked：等待时间或事件
Suspended：被显式挂起
```

单核 MCU 同一时刻通常只有一个任务真正执行；调度造成“看起来并行”。

## 任务设计

好的任务围绕职责划分：

```text
采集任务 -> 队列 -> 处理任务 -> 队列 -> 通信任务
```

不要为每个小函数创建任务，也不要让多个任务直接随意访问同一外设。

## 工具选择

| 工具 | 适合场景 |
|---|---|
| Queue | 传递带所有权的数据或消息 |
| Task Notification | 轻量的一对一事件/计数通知 |
| Binary Semaphore | 表达事件发生 |
| Counting Semaphore | 表达多个同类资源/事件 |
| Mutex | 保护共享资源，通常带优先级继承 |
| Event Group | 等待多个标志组合 |
| Software Timer | 非精密的定时回调 |

## ISR 与任务

- ISR 使用对应 `FromISR` API；
- 必要时请求中断退出后切换任务；
- ISR 不使用普通阻塞 API；
- 注意 FreeRTOS 对可调用 API 的中断优先级限制；
- 具体优先级规则以该移植层配置为准。

## 竞态示例

```c
counter++;
```

可能分成读、加、写，多任务或 ISR 交错会丢更新。`volatile` 不解决这个问题。

解决方式根据语义选择：单一所有者任务、队列、临界区、原子操作或互斥锁。

## 死锁与优先级反转

死锁常见条件：多个资源、不同获取顺序、持有并等待。统一锁顺序并减少锁范围。

低优先级任务持有高优先级任务需要的锁时可能发生优先级反转；FreeRTOS mutex 的优先级继承可缓解典型情况，但不能替代合理设计。

## 任务栈

每个任务拥有独立栈，用于局部变量、函数调用和保存现场。注意 API 中栈大小的单位可能是 `StackType_t` 元素而不是字节。

必须：

- 开启栈溢出检测；
- 观察高水位；
- 避免大数组作为任务局部变量；
- 统计所有任务、队列和堆的总 RAM。

## Tick 与延时

`vTaskDelay` 让任务阻塞，不等同于忙等待；周期任务可使用 `vTaskDelayUntil` 减少漂移。RTOS tick 不适合所有高精度时序，高精度输出仍使用硬件定时器。

## 推荐实验顺序

1. 两任务周期打印，观察调度；
2. 队列传递传感器结构体；
3. ISR 使用任务通知唤醒处理任务；
4. mutex 保护 UART 日志；
5. 故意制造竞态并修复；
6. 故意缩小任务栈并观察检测；
7. 将裸机综合项目迁移为任务架构。

## RTOS 面试最低线

能解释：

- 阻塞与忙等待的区别；
- queue、semaphore、mutex 的区别；
- 为什么 ISR 用 `FromISR`；
- `volatile` 为什么不能代替锁；
- 任务栈如何估算和检查；
- 高优先级任务为什么不能无限循环不阻塞；
- 如何避免死锁和优先级反转。
